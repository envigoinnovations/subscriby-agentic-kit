# The ports and the Core API

A **port** is an interface under `Subscriby\Connector\Contracts\Ports`: the core reaches a connector only through ports, and every method takes and returns SDK value objects from `Subscriby\Connector\Data`. The **Core API** is the inverse: interfaces under `Subscriby\Connector\Core\*` the application binds in its container and a connector asks for in a constructor, so it never imports an application class or touches a table it does not own. The `Connector` class binds each port by its interface name through the `ConnectorRegistrar`, and the registry checks the bindings against the manifest's capabilities at boot (the `connector-manifest` skill).

Rules every port shares:

- **Refs in, results out.** A port receives refs (`InstallationRef`, `IdentityRef`, `SpaceRef`, `GrantRef`, `ProjectRef`, `CreatorRef`, `MemberRef`) that carry ids and external ids, never a model, a request or a row, and returns result objects (`GrantResult`, `DeliveryResult`, `InstallationHealth`) rather than throwing on a platform refusal.
- **Credentials arrive per call.** The `CredentialBag` (`get`, `has`, `toArray`) is decrypted for one call and handed in beside the `InstallationRef`; a port never stores, logs or re-reads it from the core's table.
- **Refusals are classified, not thrown.** Every send, grant and probe reports a `DeliveryFailure` (`kind`, `detail`, `retryAfterSeconds`, `code`) built by the `FailureClassifier`; an exception is for a programming error.
- **Idempotent by design.** The core retries: `grant()` twice yields one grant, `revoke()` of what the platform already lost reports revoked, `record()` rewrites rather than duplicates, and a replayed inbound event is dropped before it reaches you.
- **Unsupported facets throw once.** A method the manifest denies throws `Subscriby\Connector\Exceptions\UnsupportedByConnector`; the core never calls a denied facet.
- **Nothing from the application's namespace.**

`InstallationRef` carries `id`, `connector`, `scope` (`platform` or `project`), `projectId`, `externalId`, `storageRef`, `handle`; `IdentityRef` `id`, `connector`, `externalId`, `storageRef`; `SpaceRef` adds `kind` and `parentExternalId`; `GrantRef` `id`, `mode`, `reference`; `DeliveryResult` `delivered`, `externalMessageId`, `failure`.

## The seven required ports

### InstallationLifecycle

`begin(InstallationRequest)` answers an `InstallationDraft` when the creator submits the install form; `complete(request, draft, credentials)` answers an `InstallationSummary` once the draft is complete (at once for a one-step connector, after the return leg for OAuth); `verify(installation, credentials)` answers an `InstallationHealth` for the Verify button, the doctor and the scheduled probe; `disconnect()` withdraws best effort; `describe()` refreshes name, handle and picture; `startLink(installation, ?payload)` builds the link that starts a conversation with the installation (a plan id, a handshake token, null for the home screen; null when the platform has none, and the portal's button comes from the no-payload answer); `publicUrl()` is where a person finds the installation with nothing to open on; `platformInstallation()` answers Subscriby's own installation for a `platform`-scope connector, else null.

The request carries `scope`, the acting `CreatorRef`, the `ProjectRef`, `fields` (every answer so far), `existing` (the installation being reconnected), `returnUrl` and `state`. The draft says what happens next: `state` to carry forward, `fields` to ask for more (the dashboard grows the form and calls `begin()` again), or `continueUrl` for the platform's own step (built on `returnUrl`; the core parks the draft with a one-time token for a quarter of an hour and calls `complete()` with `returned`, the return leg's `code` and `state`). `complete()` does the platform work (register the webhook, set the menu, fetch the profile) and answers `externalId` (the platform's stable id, never the token or a name), `displayName`, `handle`, `avatarUrl`, `meta` and `storageRef`; the core records the row itself and stores the bag merged with `meta`, which is how a secret minted at connect time (a webhook signing secret) reaches every later port call and `Core\Installations::credentials()`. Throw `InstallationRefused` when the platform refuses the credentials or another installation holds them; a refusal on `disconnect()` is logged, not thrown. `InstallationHealth` carries a `state` (`Connected`, `Degraded`, `Revoked`, `Disconnected`, `Pending`), your `reason` code, a `detail`, `creatorActionable` and the `failureKind`; use the same platform call as `RecoverySupport::probeInstallation()`.

### IdentityResolver

`resolveInbound(InboundEnvelope)` answers the acting account as an `IdentitySummary` (`externalId`, `displayName`, `username`, `avatarUrl`, `meta`) or null for an event with no actor, and never throws on an envelope it does not recognise; `describe()` is reserved for the core and yours to use for a fresh name or picture; `adopt(installation, summary)` files an account learnt outside an event (a sign-in widget, a completed handshake) as an `IdentityRecord` under your own row, the same row on a second call; `deliveryTarget(installation, credentials, IdentityRef)` answers a `Recipient` (with a `threadId` when the platform threads) or null when the installation cannot reach the account, from what you already hold, never by calling the platform. Get the id model right on day one: an `IdentityRecord` carries an `installationId` when the platform gives an account a different id per installation and null when one id names the person everywhere; the core's uniqueness is the connector, the installation and the external id. Resolving says nothing about whether the person may be in a place; keep the resolver free of authorisation.

### InboundGateway

`authenticate(Request)` returns true only when the call provably came from the platform (a signature over the body, a secret echoed in a header), naming the installation from the route and reading its stored bag through `Core\Installations::credentials()`; `decode(Request)` yields `InboundEnvelope`s (`connector`, `installation` or null, `idempotencyKey` stable per event and unique per connector, `kind` in your own vocabulary, `payload`, `receivedAt`); `immediateResponse(Request)` answers what a platform demands inside the request (an acknowledgement, a challenge echo) or null; `shouldDefer()` is reserved. Every route in `routes/inbound.php` runs behind the core's `connector.inbound:<key>` middleware, in order: an unknown connector is 404, a paused one 503 with `Retry-After`, a failed `authenticate()` 403, then `decode()` records each key with an insert that races the unique index, and when every event was seen before the gate answers your `immediateResponse()` or 204 without running your route. `decode()` is called twice (the gate, then your controller), so keep it cheap and side-effect free. A gateway-based platform with no HTTP request builds envelopes in its worker and records them through `Core\InboundEvents::accept()`.

### FailureClassifier

`classify(mixed $responseOrThrowable): DeliveryFailure`. The seven `DeliveryFailureKind`s: `Unreachable` (the account cannot be written to), `NotPermitted` (a missing right in a place; creator-actionable), `TargetMissing` (the place, message or account is gone), `RateLimited` (retryable; carry the platform's wait in `retryAfterSeconds`), `Configuration` (the installation is wrong: a revoked token, a call the manifest says the platform cannot make; creator-actionable), `Transient` (retryable), `Other` (make it rare). The core retries a retryable kind, turns a creator-actionable one into a health verdict with the connector's remedy, and records the rest as failed; on a recovery probe of an account, `TargetMissing` means the account is gone. Write the mapping as a table from the platform's codes and phrases and test it row by row; read the body, not only the status; a timeout or a DNS failure is `Transient`, never `Other`; a client-library validation error is `Configuration`. Build every port's failures through this one class.

### TextRenderer

`render(string $canonicalHtml): string`. The core emits eight tags and nothing else: `<b>`, `<i>`, `<u>`, `<s>`, `<a href>`, `<code>`, `<pre>`, `<blockquote>`; an HTML platform passes them through, a Markdown platform maps them (`**`, `*`, `__` or the words, `~~`, a Markdown link, backticks, a fenced block, `> `), a plain-text platform keeps the words (`words (url)` for a link). Two rules: the words survive whatever the platform cannot show, and plain text is the identity, byte for byte. Entities arrive encoded; a Markdown or plain renderer decodes them, an HTML renderer passes them through. A renderer never composes (no signature or footer), never truncates (the core splits before rendering) and never escapes twice.

### SettingsSchema

`installFields()` and `settingsFields(?InstallationRef)` answer `list<Field>` (`name`, `type`, `label`, `help`, `required`, `rules`, `options`, `value`, `steps`, `links`; the constructor refuses a bad name, a select without options and a link that is not `https://` or `mailto:`). A connector that declares fields in `connector.json` binds nothing: the registry binds the SDK's `ManifestSettingsSchema`, translated through `lang/*.json`. Bind your own only when the fields depend on the installation (a select over the server's channels, a `link` to the installation's own page) and then declare none in the file. With null, answer the defaults the catalogue publishes. Settings values are written by the core after validation and read back through `Core\Installations::settings()`, and `InstallationSettingsChanged` is dispatched to your `packageListeners()` after every save. A secret's value is never returned by any read; a token changes through a reconnect.

### UiSlots

`slots()` answers `list<SlotContribution>` (`slot`, a `view` in your namespace or a registered Livewire `component`, never both, and a `placeholder` view that mirrors the loaded layout), at most one per slot; an empty list is a good connector. A contribution reads only its context (SDK refs and plain values) and the connector's own services, never the core's tables, and every string comes from `lang/*.json`. The slots: `install` (beside the install form), `settings`, `resource_badge`, `resource_link_instructions`, `resource_settings`, `resource_swap`, `resource_health_detail`, `member_identity_badge`, `grant_action` (beside a place in a subscription's detail), `creator_login_method` (a sign-in button on the creator's sign-in pages), `portal_grant_action` (the member's button on the portal, with a neutral link fallback when unfilled), `payment_setup`, `checkout_method`, `access_code_redemption_hint`, `broadcast_hints`, `support_relay_options`, `recovery_actions`, `recovery_prevention`, `recovery_steps`. A slot decorates a core page and never carries a flow the REST API cannot reach; a screen of your own is `continueUrl` or `routes/web.php`.

## The capability ports

### Messenger (`messaging`, `broadcasts`)

`send(installation, credentials, Recipient, Message)` and `sendFile(installation, credentials, recipient, url, ?caption)` answer a `DeliveryResult`. A `Message` is a `body` in the canonical subset (hand it to your `TextRenderer`), `actions` built through four factories only (`url`, `callback`, `copy`, `command`, the last naming a catalogue command your `Messenger` renders into your own callback) and `meta` keyed by connector (`metaFor('<key>')`). Before you are called the core has read the per-installation switch, cut a long body into parts within `max_length` (one `send()` per part, buttons on the last), refused `sendFile()` when the manifest says no files, chosen which account to write to, paced bulk sends from `pacing`, and started the timer. Return `DeliveryResult::delivered($platformMessageId)` or `DeliveryResult::failed($this->failures->classify($response))`; read the body, because platforms refuse inside a 200. Silence is a failure: never return delivered for a refusal.

### AccessController (`access_control`, `early_admission_hold`)

`grant(installation, credentials, GrantRequest)` on a settled purchase, a materialised pending grant, a reissue or a re-admission; `revoke(installation, credentials, GrantRef, SpaceRef, IdentityRef)` on a cancellation, an expiry, a pause, a ban, a kick or an uninstall; `revokeReference()` when the reference must die while the holder stays; `admit()` when a held pass window opens (throw `UnsupportedByConnector` without the capability); `membership(installation, credentials, SpaceRef, IdentityRef)` answers a `Membership` (`Owner`, `Administrator`, `Member`, `Restricted`, `Left`, `Banned`, `Unknown`; never a guess); `announce(installation, credentials, IdentityRef, GrantAnnouncement)` tells the holder what they hold through your own `Messenger`; `reconcile(installation, credentials, iterable<GrantSnapshot>)` runs every fifteen minutes per linked resource and after an outage, letting banned holders of live grants back in and putting holders of dead grants out, answering a `ReconcileReport` (`checked`, `reasserted`, `revoked`, `failures`); assert a state rather than replay events.

`GrantRequest` carries `space`, `identity`, `mode`, `existing` (the grant being re-asserted; a stable reference such as a role is answered again, a consumable one such as a single-use link is minted fresh), `opensAt` and `meta`. Answer `GrantResult` with `granted: true` and the `reference` the core stores (the invite link, your handle, `guild:role:user`), `held: true` for a dated grant you pre-issued, or `granted: false` with the classified failure (`Unreachable` and `TargetMissing` are recorded on the grant; `NotPermitted` and `Configuration` become a health verdict). Answer `revoked: true` even when the platform reports the account already gone. A member with no identity on the connector is never asked of you; the grant waits as `pending_identity`. `AccessWindowChanged` is dispatched to your listeners when a pass window is scheduled, moved, opened, closed or cancelled. Never decide entitlement: the core's access policy does, from the ledger.

### SupportRelay (`support_relay`)

`relayModes()` returns exactly the manifest's `relay_modes`; `relay(installation, credentials, ConversationRef, Recipient, OutboundSupportMessage)` delivers a creator's reply (`body`, `attachments`, `quotedExternalId`) and answers the platform's message id; `openThread()` and `postToThread()` carry a `forum_group` conversation into one thread per member (a thread the platform no longer knows is `TargetMissing`, and the core opens a fresh one); `fetchAttachment()` hands the core a member's file once (`FetchedAttachment` with `stream`, `fileName`, `mime`, or null). The inbox is the core's: a member's message enters through your inbound handler and `Core\Support::ingest()`, a creator's answer written on the platform goes back through `Core\Support::reply()`, and the `support_relay_options` slot explains each mode.

### PortalLoginMethod (`portal_login`)

`button()` answers a `PortalLoginButton` (`label`, `icon`, both non-empty); `begin(installation, ProjectRef, HandshakeRef)` answers a `PortalLoginStart` (`token` echoed, `url` usually `startLink()` with the token in the payload, `instructions` for the manual route). Your inbound side completes it: `Core\Identities::isHandshakeToken($word)` first when the token arrived as a typed word, then `completeHandshake($token, $identityRecord, $seenBy)`, which answers `subjectName` and a `returnUrl` or throws `HandshakeRefused` (expired, held by someone else, another project's installation, wrong purpose). Creator links, member links, recovery relinks and backup identities use the same call. Only the token proves anything; never sign a member in from a name or an id you were told.

### RegistersCreators (`creator_registration`)

`signupEntry(InstallationRef $platform)` answers the link that starts the connector's own sign-up conversation on the shared installation (an empty string leaves the connector out). The conversation is yours; when the form is complete call `Core\Creators::register(new CreatorRegistration(name, email, password, identity))`, which creates the email-first account, links the vouching account as the primary identity, mails the verification link and answers a `CreatorRef`, or throws `RegistrationRefused` (`emailTaken()`, `accountRefused()`); ask `isEmailTaken()` at the step the address is typed. Sign-in for an existing creator is the `creator_login_method` slot with `Core\CreatorSessions::signIn()`, not this port.

### ManagementSurface (`management_surface`)

`commands()` returns exactly the `ManagementCommand` cases the manifest declares; `handle(InboundEnvelope)` is what your inbound route hands an admin event to (the core does not dispatch envelopes itself yet). Resolve the actor with `resolveInbound()`, find the creator with `Core\Identities::findCreator()`, and drive your screens. Every command runs the core's own action with the dashboard's validation and team authorisation, through the Core API contracts; a wizard's state lives in your own storage, never a core column. The core's messages carry `MessageAction::command()` buttons your `Messenger` renders and your `handle()` recognises. Members have their own small catalogue, `MemberCommand` (`Start`, `ReissueGrants`), outside `management_commands`. Declare what you render: start with the reads, add writes as they are built, bump the manifest each time.

### CopilotSurface (`copilot`)

`begin(CopilotTurnOpening)` opens the display the moment `Copilot::ask()` or a confirming `decide()` accepts the message, inside the connector's own request, in one platform call; `progress(handle, CopilotTurnProgress)` repaints about once a second from the worker with the reasoning, the tools in words and the answer so far (Markdown and canonical HTML); `finish(handle, CopilotTurnAnswer)` or `fail(handle, sentence)` ends the turn. The `CopilotTurnHandle` is scalars only (a draft id, a message id), carried by the core unopened. The answer carries the text twice, `links` (signed dashboard addresses), up to three `suggestions` for buttons that send back through `Copilot::ask()`, a `card` whose `actionId` your Confirm and Cancel carry to `Copilot::decide()`, `changedSomething` and the tapped `question`.

### ProvidesPaymentMethods (`native_payments`, official only)

`paymentProviders()` answers `list<NativePaymentProvider>`: `key()` as `<connector>:<provider>`, `label()`, `currencies()` (at least one), `setupFields()`, `supportsSandbox()`, `icon()`, `tagline()`, `explainer()`, `unitInUsd()` (fixed, or null for a floating currency). The core lists it under the project's payment methods, offers it at checkout through the `checkout_method` slot, records its rate and publishes it in the MCP payment-provider resource. The registry refuses the capability for a community package; gateways are the core's and never native providers.

### RecoverySupport (any `recovery_*`)

Always: `vocabulary()` (`installationNoun`, `spaceNoun`, `identityNoun`, `grantNoun`, the two plurals, optional notes; every noun non-empty), `healthReasonText(code)` (your label and remedy for a reason code, or null), `readinessChecks(installation, project)` (`ReadinessItem`s with unique keys, read from `Core\Recovery::coverage()`). `probes`: `probeInstallation()` (the same call as `verify()`), `probeSpace()` (a `SpaceAccess`: `ready`, `state`, `detail`, `creatorActionable`), `probeIdentity()` (null while the account answers, `TargetMissing` when it is gone, any other kind left alone). `standby_installations`: `registerStandbyInstallation(ProjectRef, credentials)` proves the standby, stores your row and answers an `InstallationSummary` without registering anything on the platform; `removeStandbyInstallation()` forgets it. `resource_standby`: `failOver(installation, credentials, from, to, holders)` answers a `FailOverReport`. `mirror`: `mirror(installation, credentials, from, to, externalPostId)` copies one post and answers a `DeliveryResult`. `identity_relink`: `beginIdentityHandshake(platform, CreatorRef, HandshakeRef)` answers a `PortalLoginStart` completed through `completeHandshake()`. Throw `UnsupportedByConnector::facet()` from the facets the manifest denies; the copy a connector shows about recovery carries the platform's stance on automation.

### SpaceBrowser, Announcer, InstallationActions

- `SpaceBrowser` (`space_browsing`): `browse(installation, credentials, kind)` lists every gateable place of a declared kind as `SpaceSummary` objects (`externalId`, `kind`, `title`, `parentExternalId`, `meta`), live and uncached, for the dashboard's picker, the `list_connector_spaces` tool and the automation dropdowns; the chosen place is still diagnosed before it is sold.
- `Announcer` (`announcements`): `announce(installation, credentials, Announcement)` posts a broadcast once per installation where the platform keeps a place for it, mentioning the `audience` (a list of `ResourceRef`s, empty for everyone) in your idiom, and answers a `DeliveryResult`; a `Configuration` failure (nowhere to post) falls back to per-member copies; a body over `max_length` is refused before you see it. Never a second messaging path.
- `InstallationActions` (`installation_actions`): `actions(installation)` answers the `InstallationAction`s offered right now (`key`, `label`, `description`, `fields`, `confirm`); `run(installation, credentials, action, fields)` answers `InstallationActionResult::done()` or `::refused()`, and an unknown key is refused, never thrown. Keep actions to the platform's own furniture; the REST endpoint, the `run_connector_installation_action` tool, the automations and the Copilot all run them through one door.

### SpaceCatalog (optional, no capability)

`requestLink(installation, credentials, IdentityRef, LinkRequest)` parks a request under the creator's account for a `kind` and a `LinkPurpose` (`Resource`, `Standby`, `Replacement`; `SupportRelay` reserved), one per purpose; `withdrawLinkRequest()`, `pendingLinkRequest()`, `linkInstructions(purpose)` (the sentences the dashboard shows while a request is open), `describe()` (the platform's current title and parent) and `diagnose()` (a `SpaceAccess` with your own `state` word, such as `ready`, `not_admin`, `missing_right`, `gone`). When the platform answers with the chosen place, record it with `Core\Spaces::record()` first, then `Core\Resources::create()` for a resource (idempotent on the project and the place), `Core\Recovery::registerStandby()` for a standby or `Core\Recovery::replaceSpace()` for a replacement, each the same action the dashboard runs; a refusal arrives as `ResourceRefused` or `RecoveryRefused` with the sentence to relay. Describe, do not decide: recording a place sells nothing.

## The Core API

Ask for a contract in a constructor; everything it takes and returns is a ref (names a row the core has) or a record (describes what the core should write), and every `record()` is idempotent on its natural key, so a connector may record on every event and every deploy. Every write applies the dashboard's authorisation; a `find*()` answering null means the core knows no such row; a refused write throws an exception with a stable `$reason` to branch on and a message to relay.

| Contract | What it does for a connector |
| --- | --- |
| `Installations` | `find`, `findByExternalId`, `findByStorageRef` (the read an inbound handler makes most), `listForProject`, `listPlatform`, `credentials()` (the stored bag, for a gateway verifying a signature), `settings()`; `record()`, `recordState()` (a probe's verdict with your reason code), `updateSettings()` and `updateSettingsAs()` for your declared fields, `runAction()`, `detailsForProject()` |
| `Identities` | `find`, `findByExternalId(connector, installationId, externalId)`, `findCreator`, `findMember(identity, project)`, `isHandshakeToken`; `record()`, `linkCreator()` (primary or backup; refused when another creator holds it), `linkMember()`, `completeHandshake()` |
| `Spaces` | `find`, `findByExternalId(installation, kind, externalId)`; `record()` every place you learn about; `bindResource()` for a migration binding an existing resource |
| `Resources` | `find`, `findBySpace`, `listForProject`, `memberKindLabel`, `creatorKindLabel`, `memberKindBadge`; `create()` and `createAs()` (idempotent; emits `project.resource.linked`), `detailsForProject`, `setActive`, `delete` as the creator |
| `Grants` | `find`, `findByReference` (a join request finds the purchase behind its link), `listLiveForSubscription`, `listLiveForIdentity`, `listWaitingForSubscription`; `record()` for migrations, `markHeld`, `markGranted`, `rereference`. `GrantSummary` carries mode, state (`PendingIdentity`, `Pending`, `Held`, `Granted`, `Revoked`, `Failed`), identity, reference and member |
| `Creators`, `CreatorSessions` | `register()` and `isEmailTaken()`; `signIn(record, remember)` answering `SignedIn`, `ChallengeRequired` or `Unknown` |
| `Memberships`, `Storefront` | `standingOf()` (a `MemberStanding` with the live memberships in the core's words and the waiting places), `reissueGrants()`, `cancel()`, the member's recovery email; `plansFor()`, `checkoutUrlFor()`, `portalUrl()`, `startHostedCheckout()`, `redeemAccessCode()` |
| `Projects`, `Plans`, `Coupons`, `AccessCodes`, `Broadcasts`, `PaymentSetup`, `CreatorTasks`, `PassRoster`, `PortalDesign`, `ReferralManagement`, `RetentionManagement`, `PartnerProgram` | The creator's own surface over a connector: each reads and writes as the creator a `CreatorRef` names, with the dashboard's rules, and refuses with its own exception (`ProjectRefused`, `PlanRefused`, `CouponRefused`, `AccessCodesRefused`, `BroadcastRefused`, `PaymentSetupRefused`, `CreatorTasksRefused`, `PassRosterRefused`, `ReferralRefused`) carrying `creator_unknown`, `project_unknown`, `invalid`, `tier_required`, `not_permitted` and the contract's own reasons |
| `Referrals`, `Retention`, `SmartLinks` | The member's side: the live programme, a member's standing, `join()`, `capture()`; the cancellation screen, `takeOffer()`, `declineOffer()`, `recordCheckoutStart()`, `arriveFromSequence()`; `arrive()` for a `via_<code>` deep link |
| `Alerts`, `Recovery`, `AccessWindows`, `Support`, `Copilot`, `InboundEvents`, `PaymentMethods` | Alert routing to an account; `coverage()`, `registerStandby()`, `replaceSpace()`, `openRelink()`, `completeRelink()`, `incidentsFor()`, `mirrorPairs()`, `recordMirrored()`; `listUpcoming()` windows; `ingest()`, `reply()`, `linkRelaySpace()`, `inboxFor()`, `messagesOf()`, `resolve()`, `reopen()`; `ask()` and `decide()`; `accept()` for a socket-fed connector; the provider-key rewrite a migration makes |

The flows a connector makes most: an inbound event becomes a person through `Installations::findByStorageRef()`, your `resolveInbound()`, `Identities::findByExternalId()` and then `findCreator()` or `findMember()`; a join on a bearer link goes `Grants::findByReference()` then `markGranted()`; a typed word that may be a handshake goes `isHandshakeToken()` then `completeHandshake()`; a member's home screen is `Memberships::standingOf()` with `Storefront::plansFor()` for what they could buy. Never link an account from a claim: the only paths that create a creator link are a handshake the core minted, a sign-in the platform vouched for and a registration the connector ran.

## Do not

- Do not throw for a platform refusal, swallow one, or return delivered for a message that was not.
- Do not decide entitlement, check a subscription before granting, or keep a "who is in" table of your own; read the ledger.
- Do not call the platform from `deliveryTarget()`, read a secret from a request, or record anything inside `decode()`.
- Do not compose, truncate or double-escape in the renderer, and never answer a `held` grant from a kind without early admission.
- Do not import an application class; the Core API is the only road into the core.
